# Reference: PR Template

Structure for pull request bodies generated by the ship workflow. Content is
assembled from two evidence sources in the phase directory
(`.planning/phases/<N>-<name>/`):

- `SUMMARY.md` — what was built (execute workflow output)
- `VERIFICATION_REPORT.md` — proof it works (verify workflow output)

## Body structure

```markdown
## Summary

<1–3 sentences from the plan/SUMMARY objective: what this phase delivers and
why. Plain prose, no jargon from internal tooling.>

## Changes by wave

<One bullet group per wave from PLAN.md, using SUMMARY.md details:>

### Wave 1: <wave name>
- <task summary — what changed, key files touched>
- <task summary>

### Wave 2: <wave name>
- ...

Deviations from plan (if any): <from SUMMARY.md deviations section>

## Verification evidence

- Completeness: <X>% (<n>/<m> tasks complete) — FR4.1 feature checks
- Tests: <pass/fail counts> (<test command>)
- Lint/quality: <result>
- Success criteria:
  - [x] <criterion> — <evidence: file:line or test name>
  - [x] <criterion> — <evidence>
- Gates: <passed/skipped, categories run>

Source: VERIFICATION_REPORT.md dated <date>.

## Checklist

- [ ] Verified locally (`npm test` green)
- [ ] Docs updated (README/CHANGELOG where applicable)
- [ ] No secrets or credentials committed
- [ ] Linked issue/milestone (if applicable)
```

## Rules

- Cite concrete evidence (file paths, line numbers, test names) from
  VERIFICATION_REPORT.md — never claim coverage that is not in the report
- If verification shows warnings (PASSED WITH WARNINGS), list them under
  Verification evidence rather than hiding them
- Keep Summary audience-appropriate for reviewers outside the REIS process;
  the wave detail can stay technical
